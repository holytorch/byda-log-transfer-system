[기술 과제] 대용량 로그 분석 및 전송 시스템 구축

1. 과제 개요 (Overview)
본 기술과제의 목적은 크로스 플랫폼 C++ 개발 역량, 메모리 최적화 및 예외 처리 능력을 평가하는 것입니다.
지원자는 Windows 클라이언트에서 Linux 서버로 대용량 가상 장비 로그 파일(약 500MB)을 전송하고, 서버에서 이를 파싱 및 분석하여 그 결과를 CSV 파일로 반환하는 클라이언트-서버 시스템을 개발해야 합니다.

2. 개발 환경 및 기술 스택 (Environment & Technology Stack)
클라이언트: MFC, .NET(WPF, WinForm), Qt, 오픈소스 (예, DearImGui 등등) 중 자신 있는 것 선택

서버 (Linux): C++ (Modern C++17 이상 사용 필수)

네트워크 프로토콜: TCP/IP 소켓 통신 (순수 버클리 소켓, libuv, Boost.Asio 등 C++ 네트워킹 라이브러리 사용 허용)

3. 절대 제약 사항 (STRICT CODING RULES)
아래 규칙 중 하나라도 위반할 경우 즉시 채점하지 않겠습니다.

수동 메모리 관리 전면 금지: 소스 코드의 어느 곳에서든 원시 포인터(Raw Pointer)를 위한 수동 메모리 할당 및 해제 키워드/함수(new, delete, malloc, free, calloc, realloc)의 사용을 엄격히 금지합니다.

모던 C++ RAII 패턴 강제: 모든 동적 메모리 관리는 반드시 스마트 포인터(std::make_unique, std::make_shared 등) 또는 STL 컨테이너(std::vector, std::string 등)를 사용하여 구현해야 하며, RAII 패턴을 통해 메모리 누수(Memory Leak)가 '0'이 되도록 보장해야 합니다.

4. 시스템 요구사항 (System Requirements)
A. 클라이언트 애플리케이션
UI 구성: 파일 선택기, 업로드 버튼, 실시간 진행률(%)을 보여주는 Progress Bar, 결과 다운로드 버튼이 포함된 직관적인 UI를 구현해야 합니다.

비동기 I/O (Asynchronous I/O): 파일 전송은 반드시 워커 스레드(Worker Thread)를 통해 처리되어야 합니다. 500MB 파일의 업로드/다운로드 중 메인 UI 스레드가 멈추거나(Freeze) '응답 없음' 상태가 되어서는 절대 안 됩니다.

B. 서버 애플리케이션 (Linux C++)
데몬/서비스 구동: Linux 백그라운드에서 동작하며 클라이언트의 연결 요청을 안정적으로 처리해야 합니다.

스트림 처리 (메모리 제약): 서버는 500MB의 로그 파일을 수신하는 동시에 파싱하거나, 버퍼(Buffer) 단위로 나누어 읽어야 합니다.
500MB 파일 전체를 한 번에 메모리에 로드하는 방식은 절대 금지됩니다. (프로세스의 최대 메모리 사용량은 50MB 이하 유지를 권장합니다).

데이터 파싱 작업: std::string 연산 또는 정규식(Regex)을 사용하여 제공된 로그 파일을 분석합니다.

작업 1: 특정 모듈의 발생 발생 횟수를 시간대별로 그룹화하여 산출. (로그 파싱 필요..)

작업 2: spd 문자열이 포함된 라인에서 속도값을 추출하여 평균 속도를 계산.

CSV 생성: 분석된 통계 데이터를 구조화된 result.csv 포맷으로 생성한 뒤, 작업이 완료되면 클라이언트에게 전송합니다.

5. 핵심 평가 기준 (Core Evaluation Criteria)
메모리 누수 및 RAII 준수 여부: new/malloc 금지 규칙의 완벽한 준수. 

예외 처리 (독약 데이터 대응): 제공된 500MB 로그 파일에는 약 0.001%의 비율로 의도적으로 훼손된 데이터(괄호 누락, 예상치 못한 문자, 포맷 불일치 등)가 포함되어 있습니다.
서버는 이 라인들을 처리할 때 절대 다운(Segmentation Fault, 런타임 에러)되어서는 안 됩니다. 비정상 데이터를 감지하여 안전하게 예외 처리(해당 라인 스킵 및 로그 기록)한 후, 나머지 정상 라인의 파싱을 끝까지 완료해야 합니다.

네트워크 견고성: 대용량 파일 전송 도중 네트워크 연결이 강제로 끊어질 경우, 클라이언트와 서버 모두 크래시(Crash) 없이 소켓 에러를 안전하게 처리하고 사용 중이던 자원을 정상적으로 시스템에 반환해야 합니다.
